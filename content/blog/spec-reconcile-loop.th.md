วงจร reconcile สำหรับ spec ทำงานเหมือน controller ใน Kubernetes: คนเปลี่ยนสถานะที่ต้องการ (spec) เอเจนต์เทียบกับสถานะจริง (โค้ด) แล้วปรับโค้ดให้ตรง และเทสต์วัดผลลัพธ์ เทสต์ที่ผ่านทั้งหมดตรวจเฉพาะสิ่งที่เขียนไว้ในเทสต์ ดังนั้นทุก MUST ต้องมีการตรวจของตัวเอง และสภาพแวดล้อมของเอเจนต์ต้องมีการรันโค้ด เทสต์ ล็อก ข้อมูล บริการ และ sandbox

<b-chapter id="k8s" title="วงจรเดียวกับใน Kubernetes" icon="hub" sw="1.6">
  <b-why align="left">Kubernetes เป็นระบบที่รันบริการและดูแลให้ทำงานต่อเนื่องบนเซิร์ฟเวอร์จำนวนมาก แนวคิดหลักเรียบง่าย: คนเขียนคำอธิบายว่าควรเป็นอย่างไร ("ให้มีบริการสามชุดเสมอ") แล้วโปรแกรมผู้ดูแลที่เรียกว่า controller เทียบคำอธิบายกับสิ่งที่มีอยู่จริงอยู่ตลอดและแก้ส่วนที่ต่าง นี่คือวงจร reconcile สำหรับ spec ก็ใช้แผนเดียวกัน: คนกำหนดสถานะที่ต้องการ และเอเจนต์ปรับโค้ดให้ตรงได้</b-why>
  <b-why>สถานะที่ต้องการในที่นี้คือ<a href="/blog/specs-by-aggregates/">พจนานุกรม aggregate</a>: หนึ่งรายการต่อหนึ่งแนวคิด และข้อกำหนดที่ระบุ MUST และ SHOULD</b-why>

  <b-why align="left">วิธีอ่านภาพ สี่คอลัมน์คือสี่บทบาทของวงจร สองแถวคือสองระบบ และแถวที่สามอธิบายศัพท์ด้วยคำง่าย ๆ สถานะที่ต้องการ (ช่องที่เติมสี) คือสิ่งที่คนเปลี่ยน ใน Kubernetes คือ chart และ manifest: ไฟล์ที่บอกว่าส่วนใดของบริการต้องรันและกี่ชุด ใน spec คือพจนานุกรม aggregate ที่มีคำว่า MUST ("จำเป็น") และ SHOULD ("แนะนำ") ผู้ลงมือทำให้สถานะจริงตรงกับสถานะที่ต้องการ: ใน Kubernetes คือ controller ใน spec คือเอเจนต์ สถานะจริงคือสิ่งที่มีอยู่ตอนนี้: node (เซิร์ฟเวอร์) และ pod (ส่วนของบริการที่รันบนนั้น) หรือโค้ด ตัววัดบอกว่าตรงกันหรือไม่: probe (การตรวจอัตโนมัติสั้น ๆ ว่า "ยังทำงานอยู่ไหม") และเมตริก หรือเทสต์และการตรวจคุณภาพ ลูกศรลงด้านบนหมายความว่าคนเปลี่ยนเฉพาะสถานะที่ต้องการ ลูกศรวนด้านล่างหมายความว่าผลการวัดย้อนกลับไปหาผู้ลงมือ วนไปจนกว่าจะตรงกัน ตัวอย่าง: คนเขียนในพจนานุกรมว่า "การจองปิดหลัง 15 นาที" เอเจนต์แก้โค้ด เทสต์ตรวจ และเทสต์ที่ไม่ผ่านส่งเอเจนต์กลับไปที่โค้ด</b-why>
  <b-cap>วงจร reconcile อ้างอิง<a href="https://kubernetes.io/docs/concepts/architecture/controller/" target="_blank" rel="noopener">เอกสาร Kubernetes เรื่อง controller</a></b-cap>
  <b-finding>
    <ex>ใน Kubernetes คนแก้ chart และ controller ปรับ node ให้ตรง ที่นี่คนแก้พจนานุกรม และเอเจนต์ปรับโค้ดให้ตรงแล้วตรวจด้วยเทสต์</ex>
    <gen>ทั้งสองระบบแยกสถานะที่ต้องการออกจากสถานะจริง แล้ว reconcile กันเป็นวงจร คนในวงจรเปลี่ยนเฉพาะสถานะที่ต้องการ ทุกการแก้จึงกลายเป็นงานของผู้ลงมือทันที</gen>
    <do>แก้ข้อกำหนดในพจนานุกรม แทนการแก้โค้ดด้วยมือ และสั่งให้เอเจนต์ปรับโค้ดให้ตรงกับพจนานุกรม</do>
  </b-finding>
</b-chapter>
<b-chapter id="sensors" title="การตรวจเห็นเฉพาะสิ่งที่ใส่ไว้ในมัน" icon="gauge">
  <b-why align="left">การตรวจแสดงเฉพาะสิ่งที่ใส่ไว้ในมัน ใน Kubernetes probe คือคำขอสั้น ๆ อัตโนมัติไปยังบริการว่า "ตอบสนองอยู่ไหม" ถ้าบริการตอบ "200" (รหัสสำเร็จ) probe ก็เป็นสีเขียว ทั้งที่บริการอาจไม่ได้ทำสิ่งสำคัญที่สุด เช่น คิวออเดอร์ค้าง ใน spec ก็เป็นแบบเดียวกันกับเทสต์ ถ้าข้อกำหนดไม่มีเทสต์ เทสต์ทั้งหมดจะยังเขียวและไม่มีใครสังเกตว่าข้อกำหนดนั้นยังไม่เป็นจริง</b-why>
  <b-why>ตัวอย่างคือการจองห้องประชุมจาก<a href="/blog/specs-by-aggregates/">ข้อกำหนดแบ่งตาม aggregate</a>: MUST สามข้อและ SHOULD หนึ่งข้อ</b-why>

  <b-why align="left">วิธีอ่านภาพ ด้านซ้ายคือ Kubernetes: probe ได้คำตอบ "200: ทำงานอยู่" จึงเป็นสีเขียว แต่ออเดอร์ไม่ถูกประมวลผล แปลว่า probe ไม่ได้ตรวจสิ่งสำคัญที่สุด ด้านขวาคือ spec ด้วยตัวอย่างการจองห้องประชุม: MUST สามข้อและ SHOULD หนึ่งข้อ MUST สองข้อมีเทสต์ครอบคลุม (การจองไม่ทับกัน สถานะเดินไปข้างหน้าเท่านั้น) ข้อที่สาม "หากไม่ยืนยัน การจองปิดหลัง 15 นาที" ไม่มีใครตรวจ คนรีวิว SHOULD เรื่องช่องทาง MUST ครอบคลุม 2 จาก 3 คือ 67% กฎสามข้อใต้แผนภาพ: ทุก MUST มีการตรวจของตัวเอง MUST ที่ไม่มีการตรวจนับเป็นช่องโหว่ที่ต้องปิด ผลสีเขียวยังไม่ได้แปลว่าทุกอย่างถูกต้อง</b-why>
  <b-cap>probe มีแบบไหนและตรวจอะไร: <a href="https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/" target="_blank" rel="noopener">Kubernetes: probe</a></b-cap>
  <b-finding>
    <ex>probe ตอบ "200" ขณะที่ออเดอร์ค้าง และเทสต์การจองเขียวขณะที่ไม่มีใครตรวจกฎ 15 นาที</ex>
    <gen>การตรวจยืนยันเฉพาะสิ่งที่เขียนไว้ในมัน และไม่บอกอะไรเกี่ยวกับส่วนที่เหลือ จึงต้องนำการ์ด aggregate มาเทียบกับการตรวจ: MUST ที่ไม่มีการตรวจคือช่องโหว่ ไม่ใช่ข้อกำหนดที่เป็นจริงแล้ว</gen>
    <do>ไล่ดู MUST ในพจนานุกรมของคุณและทำเครื่องหมายข้อที่ไม่มีเทสต์ แปลงแต่ละข้อเป็นงาน หรือลดระดับเป็น SHOULD อย่างตั้งใจ</do>
  </b-finding>
</b-chapter>
<b-chapter id="env" title="สภาพแวดล้อมเป็นตัวกำหนดว่าวงจรจะปิดหรือไม่" icon="terminal-screen">
  <b-why align="left">วงจรปิดได้ก็ต่อเมื่อผู้ลงมือมีทุกอย่างที่จำเป็นสำหรับการเทียบ controller ของ Kubernetes ทำงานได้เพราะคลัสเตอร์ให้การเข้าถึงทุกสิ่งที่ต้องใช้ สำหรับเอเจนต์ สภาพแวดล้อมนี้เรียกว่า harness: สภาพแวดล้อมที่มันทำงาน พร้อมโปรแกรม สิทธิ์ และการตรวจ</b-why>

  <b-cta href="/blog/ai-in-code-harness-and-tools/" k="บทความแยก" t="เลือกสภาพแวดล้อม: เปรียบเทียบ harness" icon="terminal-screen" sw="1.8">Claude Code, Codex, Cursor, Hermes และแชตบนแผนที่เดียว</b-cta>
  <b-why align="left">ความสามารถหกอย่างในภาพคือสิ่งที่เอเจนต์ต้องมีเพื่อปิดวงจร และสิ่งที่เกิดขึ้นเมื่อขาดแต่ละอย่าง ไม่มีการรันโค้ด เอเจนต์ต้องเดาว่าโปรแกรมทำงานอย่างไร ไม่มีเทสต์ ก็ตรวจ MUST ไม่ได้ ไม่มีล็อก ก็มองไม่เห็นว่าอะไรพังกันแน่ ไม่มีข้อมูลทดสอบ การตรวจจะรันบนฐานข้อมูลว่างและไม่แสดงอะไร ไม่มีบริการผ่าน MCP การตรวจการเชื่อมต่อก็ทำแบบมองไม่เห็น ไม่มี sandbox (พื้นที่แยกที่ลองและพังได้อย่างปลอดภัย) ก็น่ากลัวเกินกว่าจะให้เอเจนต์ลงมือ ถ้าขาดความสามารถใดไป วงจรจะเปิดอยู่ตรงจุดนั้น</b-why>
  <b-finding>
    <ex>controller ของ Kubernetes ทำงานได้เพราะคลัสเตอร์ให้ API, node และ probe สำหรับวงจรเดียวกัน เอเจนต์ต้องรันโค้ด เทสต์ ล็อก ข้อมูล บริการ และ sandbox ได้</ex>
    <gen>พจนานุกรมกำหนดสถานะที่ต้องการ แต่เฉพาะผู้ที่รันและวัดโค้ดได้เท่านั้นที่ reconcile โค้ดกับสถานะนั้นได้ สิ่งใดที่สภาพแวดล้อมไม่มี เอเจนต์ตรวจไม่ได้ และวงจรยังเปิดอยู่ตรงจุดนั้น</gen>
    <do>ทำเครื่องหมายว่าเอเจนต์ของคุณมีความสามารถหกอย่างนี้ข้อไหนบ้าง สำหรับข้อที่ขาด ให้ตัดสินใจว่าจะเพิ่มลงใน harness หรือเปลี่ยน harness</do>
  </b-finding>

    <q t="คนเปลี่ยนอะไรในวงจรนี้?">เฉพาะสถานะที่ต้องการ คือ spec ทุกการแก้กลายเป็นงานของเอเจนต์ทันที</q>
