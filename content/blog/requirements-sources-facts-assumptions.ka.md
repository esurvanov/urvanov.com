AI აგენტი მოთხოვნებს თავდაჯერებულად წერს და მისი ვარაუდები ფაქტებს ჰგავს. ყოველი პუნქტისთვის მოითხოვეთ დამადასტურებელი: წყაროს ბმული, მოდელის ვარაუდები და სტატუსი „ფაქტია თუ არა“; წყაროები MCP-ით მიაერთეთ, უკეთესია Git-იდან. პატარა შესწორებებს აგენტი თავად აკეთებს, დიდზე ადამიანი წყვეტს. საფუძველი: [MCP AI აგენტისთვის](/blog/mcp-agent-access/#facts).

<b-chapter id="what" icon="shield-check" title="რა მოვითხოვოთ აგენტისგან">
  <b-why align="left">აგენტი შეხვედრის ჩანაწერებსა და დოკუმენტებს გლუვად გადმოსცემს და ტექსტიდან არ ჩანს, სად მთავრდება ფაქტი და სად იწყება ვარაუდი. ეს მოდელის მუშაობის პრინციპიდანაა: ის ტექსტს დამაჯერებლად აგრძელებს, ხოლო მონაცემების ხვრელს გლუვი ფრაზით ავსებს. ამიტომ მოთხოვნებისა და ჩანაწერების ყოველ პუნქტს სამი რამ სჭირდება: დამადასტურებელი (წყაროს ბმული ციტატით), ვარაუდი (რაც აგენტმა თავად შეავსო) და სტატუსი (ფაქტია, არაა ფაქტი ან კითხვაა ადამიანისთვის).</b-why>
  <iso-art name="requirements-sources-facts-assumptions/marks"></iso-art>
  <b-why align="left">სურათზე ერთსა და იმავე პუნქტზე სამი სახის ნიშანია. წყარო პასუხობს კითხვას „საიდან არის აღებული“: ბმული ფაილზე ან ციტატა შეხვედრის ჩანაწერიდან დროის მითითებით. ვარაუდი პასუხობს კითხვას „რა შეავსო აქ მოდელმა“: მაგალითად, ჩანაწერში წერია „ბარათით ვიხდით“, ვალუტაზე არაფერია, აგენტმა კი დაწერა „რუბლით“. ასეთი ვარაუდი ფაქტებისგან განცალკევებულ ცალკე ხაზზე უნდა იდგეს. სტატუსი პასუხობს კითხვას „შეიძლება თუ არა ამაზე დაყრდნობა“: „ფაქტი“, თუ დამადასტურებელი არსებობს, „არაა ფაქტი“, თუ არ არსებობს, და „კითხვა“, თუ გადაწყვეტილება ადამიანმა უნდა მიიღოს.</b-why>

<b-chapter id="sources" icon="plug" title="წყაროები MCP-ით: Git ყველაზე კარგად მუშაობს">
  <b-why align="left">ნიშანი „წყარო“ მხოლოდ მაშინ მუშაობს, თუ აგენტი ფაქტებს რეალური სისტემებიდან იღებს და არ იხსენებს. ამისთვის აგენტი სისტემებს MCP-ით უერთდება: თავად ხსნის ფაილს, შეხვედრის ჩანაწერს ან გვერდს და ციტირებს სწორ ადგილს<b-proof href="https://modelcontextprotocol.io/docs/getting-started/intro" quote="MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems."/>. მაგრამ წყაროები სხვადასხვა ხარისხით სანდოა. ყველაზე კარგად Git ერგება: მოთხოვნები ფაილებად ცხოვრობს კოდის გვერდით, ყოველ შესწორებას აქვს ავტორი, თარიღი და მიზეზი, ადრინდელი ვერსიები ისტორიაში ჩანს. Confluence კარგია მხოლოდ მოწესრიგებული გვერდებით: თითოეულს ჰყავს მფლობელი და შემოწმების თარიღი, მოძველებული კი დაარქივებულია. თორემ აგენტი ძველ გვერდს ფაქტად წაიკითხავს და ჰალუცინაციას გამოიღებს, თუმცა მოდელს თავისით არაფერი გამოუგონია. ცალკე წყაროა შეხვედრის ჩანაწერები: რაზე შეთანხმდნენ, ჩანაწერის ბმულით. მაგრამ შეთანხმებული და კოდში არსებული შეიძლება დაშორდეს ერთმანეთს, ამიტომ ის Git-ში რეალურად მყოფს უნდა შეადარდეს: შეხვედრები და კოდი ხშირად სინქრონიდან გადადის.</b-why>
  <iso-art name="requirements-sources-facts-assumptions/sources-mcp"></iso-art>
  <b-why align="left">სურათის მარჯვნივ სამი სახის წყაროა, მარცხნივ — შედეგი. აგენტი მათ MCP-ით უერთდება (მავთულები შტეკერებით), იღებს ფაქტებს და წერს მოთხოვნებს, სადაც ყოველ პუნქტს აქვს ბმული და სტატუსი. Git პირველია: ის მთავარი წყაროა. Confluence წყვეტილი ხაზითაა დახატული: ის მხოლოდ მაშინ უერთდება, როცა გვერდები აქტუალურია. შეხვედრის ჩანაწერები ცალკე წყაროა: აგენტი მათგან იღებს შეთანხმებულს ბმულითა და დროით. შეთანხმებული კოდს Git-ში უნდა შეადარდეს: შეხვედრები და კოდი სინქრონიდან გადადის.</b-why>
  <b-why align="left">წყაროების რეესტრში შენახვა მოსახერხებელია: ერთი სტრიქონი ერთ წყაროზე. ცხრილს სამი სვეტი აქვს: ბმული (სად წახვიდეთ), აღწერა (რა არის იქ და რამდენად ახალია) და ტიპი (Git, შეხვედრის ჩანაწერი, Confluence). ყოველი მოთხოვნის ხაზში „წყარო“ აგენტი ამ რეესტრიდან ბმულს ათავსებს.</b-why>

  <b-why align="left">use case (განმარტებით, სისტემის ქცევის სტრუქტურირებული აღწერა გარე მონაწილეთა მოთხოვნებზე რეაგირებისას<b-proof href="https://en.wikipedia.org/wiki/Use_case" quote="structured description of a system’s behavior as it responds to requests from external actors"/>) არის მოთხოვნის გამოყენების ერთი სცენარი. მოთხოვნას „ბარათით გადახდა“ სამი აქვს: ჩვეულებრივი გადახდა, ბანკის უარი და განმეორებითი გადახდა. ისინი ცალკე იწერება, რადგან შესწორება ჩვეულებრივ ერთ-ორ სცენარს ეხება და სწორედ ისინი უნდა გადაამოწმო. ეს წინა თავთან კავშირია: დიდი შესწორება ქცევას ცვლის, ამიტომ აგენტი ჩამოთვლის ზემოქმედების ქვეშ მოხვედრილ use case-ებსა და მათ ტესტებს. პატარა შესწორება ქცევას არ ცვლის და აგენტი მხოლოდ ადასტურებს, რომ use case-ები უცვლელია. ასე პატარა შესწორება მთელი მოთხოვნის გადამოწმებას არ ნიშნავს.</b-why>
  <iso-art name="requirements-sources-facts-assumptions/use-cases"></iso-art>
  <b-why align="left">სურათი ამას მაგალითით აჩვენებს. მარცხნივ მოთხოვნაა „ბარათით გადახდა“. მარჯვნივ მისი სამი use case-ია: ჩვეულებრივი გადახდა (მყიდველი მაშინვე იხდის), ბანკის უარი (შეცდომა და განმეორება) და განმეორებითი გადახდა (დაცვა ორმაგი ჩამოჭრისგან). ძახილის ნიშანი მესამეზეა: ვთქვათ, შეხვედრაზე გადაწყვიტეს ორმაგი ჩამოჭრისგან დაცვის შეცვლა. ეს დიდი შესწორებაა და ის მხოლოდ განმეორებით გადახდას ეხება. აგენტი ჩამოთვლის ზუსტად ამ use case-სა და მის ტესტებს, ჩვეულებრივი გადახდა და ბანკის უარი კი უცვლელი რჩება.</b-why>
  <b-pills>
    <pill>Case: ჩვეულებრივი გზა</pill>
    <pill>Case: შეცდომა</pill>
    <pill>Case: განმეორება</pill>
  </b-pills>
  <b-why align="left">მაგალითი. შეხვედრაზე გადაწყვიტეს, რომ ერთი წუთის განმავლობაში განმეორებითი გადახდა იმავე შეკვეთად ითვლება. ეს დიდი შესწორებაა და ის მხოლოდ use case-ს „განმეორება“ ეხება. მისთვის აგენტი ჩამოთვლის განსაახლებელ ტესტებს, მაგალითად, „30 წამში მეორე გადახდა ორჯერ არ ჩამოჭრის“. use case-ები „ჩვეულებრივი გზა“ და „შეცდომა“ უცვლელი რჩება და მათი ტესტები ისე გადის. თუ ასეთი სია არ არის, ზემოქმედების ქვეშ მოხვედრილ use case-ს მომხმარებლები აღმოაჩენენ.</b-why>
  <b-finding>
    <ex>მოთხოვნა „ბარათით გადახდა“ სამ case-ად იყოფა და განმეორებით გადახდაზე შესწორება მხოლოდ მესამეს ეხება.</ex>
    <gen>დიდი შესწორებისას აგენტი ჩამოთვლის ზემოქმედების ქვეშ მოხვედრილ case-ებს, პატარასას კი ადასტურებს, რომ case-ები არ შეცვლილა.</gen>
    <do k="რა ვქნათ">ყოველი შესწორების შემდეგ სთხოვეთ აგენტს ზემოქმედების ქვეშ მოხვედრილი case-ებისა და მათი ტესტების ჩამოთვლა.</do>
