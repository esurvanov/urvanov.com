เอเจนต์เขียนข้อกำหนดอย่างมั่นใจ และสิ่งที่มันเดาก็ดูเหมือนข้อเท็จจริง ให้เรียกร้องหลักฐานสำหรับทุกรายการ คือลิงก์แหล่งที่มา สมมติฐานของโมเดล และสถานะ "ข้อเท็จจริงหรือไม่" แล้วเชื่อมแหล่งข้อมูลผ่าน MCP โดยเฉพาะจาก Git เอเจนต์แก้ส่วนเล็กเอง ส่วนการแก้ใหญ่คนเป็นผู้ตัดสิน พื้นฐาน: [MCP สำหรับเอเจนต์ AI](/blog/mcp-agent-access/#facts)

<b-post series="harness">

<b-chapter id="what" icon="shield-check" title="ต้องเรียกร้องอะไรจากเอเจนต์">
  <b-why align="left">เอเจนต์สรุปบันทึกการประชุมและเอกสารได้ลื่นไหล และตัวข้อความไม่ได้บอกว่าข้อเท็จจริงจบตรงไหนและการเดาเริ่มตรงไหน นี่เป็นผลจากการทำงานของโมเดล: มันต่อข้อความอย่างสมเหตุสมผล และช่องว่างของข้อมูลถูกเติมด้วยประโยคที่ลื่นไหล ดังนั้นทุกรายการในข้อกำหนดและบันทึกต้องมีสามอย่าง: หลักฐาน (ลิงก์แหล่งที่มาพร้อมคำพูดที่ยกมา) สมมติฐาน (สิ่งที่เอเจนต์เติมเอง) และสถานะ (ข้อเท็จจริง ไม่ใช่ข้อเท็จจริง หรือคำถามสำหรับคน)</b-why>
  <iso-art name="requirements-sources-facts-assumptions/marks"></iso-art>
  <b-why align="left">ภาพแสดงเครื่องหมายสามชนิดบนรายการเดียวกัน แหล่งที่มาตอบว่า "นำมาจากไหน": ลิงก์ไปยังไฟล์ หรือคำพูดจากการบันทึกการประชุมพร้อมเวลา สมมติฐานตอบว่า "โมเดลเติมอะไรตรงนี้": เช่น การบันทึกบอกว่า "ชำระด้วยบัตร" ไม่ได้พูดถึงสกุลเงิน แต่เอเจนต์เขียนว่า "เป็นรูเบิล" การเดาแบบนี้ต้องอยู่ในบรรทัดของตัวเอง แยกจากข้อเท็จจริง สถานะตอบว่า "พึ่งพาได้หรือไม่": "ข้อเท็จจริง" ถ้ามีหลักฐาน "ไม่ใช่ข้อเท็จจริง" ถ้าไม่มี และ "คำถาม" ถ้าคนต้องตัดสินใจ</b-why>
  <b-table id="marks-example">

| | ไม่มีเครื่องหมาย | มีเครื่องหมาย |
|---|---|---|
| รายการ | “ชำระด้วยบัตรเป็นรูเบิล” | “ชำระด้วยบัตร” |
| แหล่งที่มา | ไม่ระบุ | ประชุมวันที่ 12 ต.ค. 14:32 “ลูกค้าชำระด้วยบัตรตอนเช็กเอาต์” |
| สมมติฐาน | ซ่อนอยู่ในข้อความ: “เป็นรูเบิล” | อยู่ในบรรทัดของตัวเอง: “ชำระเป็นรูเบิลเท่านั้น” |
| สถานะ | อ่านเหมือนข้อเท็จจริง | ไม่ใช่ข้อเท็จจริง: ที่ประชุมไม่ได้พูดถึงสกุลเงิน |
| ผู้อ่านทำอะไร | เชื่อตามนั้น | ตรวจสมมติฐานหรือถามคำถาม |

  </b-table>
  <b-rules sw="1.8">
    <rule icon="key" t="ลิงก์ (หลักฐาน)">ลิงก์ไปยังเอกสาร หรือคำพูดจากบันทึกการประชุมพร้อมเวลา</rule>
    <rule icon="help" t="สมมติฐาน">สิ่งที่เอเจนต์เติมเองเขียนไว้ในบรรทัดแยก</rule>
    <rule icon="shield-check" t="สถานะ">ข้อเท็จจริง ไม่ใช่ข้อเท็จจริง หรือคำถามสำหรับคน</rule>
  </b-rules>
  <b-why align="left">กฎง่าย ๆ: ไม่มีแหล่งที่มา หมายถึงสถานะ "ไม่ใช่ข้อเท็จจริง" รายการที่ไม่มีหลักฐานจึงไม่กลายเป็นข้อกำหนดโดยไม่มีใครสังเกต คนเห็นรายการแบบนี้เป็นรายการแล้วตัดสินใจว่าจะทำอย่างไร: หาแหล่งที่มา ยืนยันในที่ประชุม หรือตัดทิ้ง เครื่องหมายช่วยให้ตรวจเร็วขึ้น: คำพูดที่มีเวลาตรวจได้ในไม่กี่วินาที และบรรทัดสมมติฐานชี้ว่าควรหาข้อผิดพลาดตรงไหน แหล่งข้อมูลหาได้จากไหนอยู่ในบทถัดไป และสิ่งที่ต้องทำเมื่อรายการเปลี่ยนอยู่ถัดจากนั้น</b-why>
  <b-finding>
    <ex>ทุกรายการมีแหล่งที่มา บรรทัดแยกสำหรับสิ่งที่เดา และสถานะ</ex>
    <gen>รายการที่ไม่มีแหล่งที่มาได้สถานะ "ไม่ใช่ข้อเท็จจริง" และคนตรวจก่อนพึ่งพา นี่ต่อยอดแนวคิดจากส่วน [hallucination ในบทความ MCP](/blog/mcp-agent-access/#facts)</gen>
    <do k="ควรทำ">เพิ่มเครื่องหมายสามอย่างลงในเทมเพลตข้อกำหนดและบันทึกการประชุมของคุณ</do>
  </b-finding>
</b-chapter>

<b-chapter id="sources" icon="plug" title="แหล่งที่มาผ่าน MCP: Git ได้ผลดีที่สุด">
  <b-why align="left">เครื่องหมาย "แหล่งที่มา" ใช้ได้ผลก็ต่อเมื่อเอเจนต์ดึงข้อเท็จจริงจากระบบจริง แทนการนึกเอา สำหรับสิ่งนี้เอเจนต์ถูกเชื่อมกับระบบผ่าน MCP: มันเปิดไฟล์ การบันทึกการประชุม หรือหน้าเอกสารเอง แล้วยกคำพูดจากตำแหน่งที่ถูกต้อง<b-proof href="https://modelcontextprotocol.io/docs/getting-started/intro" quote="MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems."/> แต่แหล่งข้อมูลเชื่อถือได้ไม่เท่ากัน Git เหมาะที่สุด: ข้อกำหนดอยู่เป็นไฟล์ข้างโค้ด ทุกการแก้มีผู้แก้ วันที่ และเหตุผล และเห็นเวอร์ชันก่อนหน้าในประวัติ Confluence ใช้ได้ก็ต่อเมื่อหน้าเอกสารได้รับการดูแลดี: แต่ละหน้ามีเจ้าของและวันที่ตรวจ และหน้าที่ล้าสมัยถูกเก็บเข้าคลัง มิฉะนั้นเอเจนต์จะอ่านหน้าเก่าเป็นข้อเท็จจริงและสร้าง hallucination ทั้งที่โมเดลไม่ได้แต่งอะไรเอง แหล่งข้อมูลอีกอย่างคือบันทึกการประชุม: สิ่งที่ตกลงกัน พร้อมลิงก์ไปยังการบันทึก แต่สิ่งที่ตกลงกันกับสิ่งที่อยู่ในโค้ดอาจเหลื่อมกันได้ จึงต้องตรวจเทียบกับสิ่งที่อยู่ใน Git จริง ๆ: การประชุมกับโค้ดมักไม่ตรงกัน</b-why>
  <iso-art name="requirements-sources-facts-assumptions/sources-mcp"></iso-art>
  <b-why align="left">ด้านขวาของภาพคือแหล่งข้อมูลสามประเภท ด้านซ้ายคือผลลัพธ์ เอเจนต์เชื่อมกับแหล่งเหล่านี้ผ่าน MCP (สายไฟที่มีปลั๊ก) ดึงข้อเท็จจริง และเขียนข้อกำหนดที่ทุกรายการมีลิงก์และสถานะ Git มาก่อน: เป็นแหล่งหลัก Confluence วาดด้วยเส้นประ: เชื่อมเฉพาะเมื่อหน้าเอกสารเป็นปัจจุบัน การบันทึกการประชุมเป็นแหล่งแยกต่างหาก: เอเจนต์ดึงสิ่งที่ตกลงกันจากที่นั่น พร้อมลิงก์และเวลา สิ่งที่ตกลงกันต้องตรวจเทียบกับโค้ดใน Git: การประชุมกับโค้ดมักไม่ตรงกัน</b-why>
  <b-why align="left">สะดวกที่จะเก็บแหล่งข้อมูลไว้ในทะเบียน: หนึ่งแถวต่อหนึ่งแหล่ง ตารางมีสามคอลัมน์: ลิงก์ (ไปที่ไหน) คำอธิบาย (มีอะไรและใหม่แค่ไหน) และประเภท (Git, การบันทึกการประชุม, Confluence) ในบรรทัด "แหล่งที่มา" ของทุกข้อกำหนด เอเจนต์ใส่ลิงก์จากทะเบียนนี้</b-why>
  <b-table id="sources-registry">

| ลิงก์ | คำอธิบาย | ประเภท |
|---|---|---|
| git.example.com/shop/requirements/payments.md | ข้อกำหนด “ชำระด้วยบัตร”; เห็นประวัติการแก้ ผู้แก้ และเหตุผลใน commit | Git: ไฟล์ |
| git.example.com/shop/requirements/tags | เวอร์ชันของข้อกำหนด: v1.1, v2.0 | Git: tag |
| tldv.io/meeting/12-10 | การบันทึกประชุมวันที่ 12 ต.ค.: สิ่งที่ตกลงกัน คำพูดพร้อมเวลา; ตรวจเทียบกับโค้ด เพราะอาจไม่ตรงกัน | ข้อตกลง: บันทึกการประชุม |
| confluence.example.com/pay-rules | กฎการชำระเงิน; หน้านี้มีเจ้าของ ตรวจเมื่อ 1 ต.ค. | Confluence เฉพาะหน้าที่เป็นปัจจุบัน |

  </b-table>
  <b-finding>
    <ex>เอเจนต์ดึงข้อเท็จจริงผ่าน MCP จากทะเบียนแหล่งข้อมูล และทุกข้อกำหนดมีลิงก์จากทะเบียนนั้น</ex>
    <gen>บันทึกการประชุมแสดงสิ่งที่ตกลงกัน และต้องตรวจเทียบกับโค้ดใน Git: การประชุมกับโค้ดมักไม่ตรงกัน ใน Git การแก้มีผู้แก้ วันที่ และเหตุผล และเวอร์ชันของข้อกำหนดตรงกับ tag การตรวจและการย้อนกลับจึงง่าย หน้า Confluence ที่ไม่มีเจ้าของและไม่มีวันที่ตรวจจะล้าสมัยโดยไม่มีใครสังเกต และเอเจนต์เล่าข้อความเก่าซ้ำเป็นข้อเท็จจริง</gen>
    <do k="ควรทำ">เริ่มทะเบียนสามคอลัมน์: ลิงก์ คำอธิบาย ประเภท เริ่มจาก Git และเพิ่มหน้า Confluence หลังตรวจแล้วเท่านั้น: มีเจ้าของ มีวันที่ และส่วนเกินถูกเก็บเข้าคลัง</do>
  </b-finding>

  <b-say-agent title="บอกเอเจนต์" plain>วิเคราะห์บันทึกการประชุมแล้วเขียนรายการข้อกำหนด สำหรับทุกรายการให้ระบุแหล่งที่มา (ลิงก์จากทะเบียนและคำพูดพร้อมเวลา) สมมติฐานของคุณในบรรทัดแยก และสถานะ: ข้อเท็จจริง ไม่ใช่ข้อเท็จจริง หรือคำถาม หากไม่มีแหล่งที่มา ให้ระบุว่า “ไม่ใช่ข้อเท็จจริง”</b-say-agent>
  <b-why align="left">prompt ขอให้เอเจนต์แยกการบันทึกเป็นรายการ แต่ละรายการมีเครื่องหมายสามอย่าง ประโยคสุดท้ายสำคัญ: ห้ามถือว่ารายการเป็นข้อเท็จจริงเมื่อไม่มีแหล่งที่มา prompt แบบนี้ใช้ได้กับการบันทึกการประชุม อีเมล เธรดแชต และเอกสารทุกประเภท</b-why>

  <b-why align="left">รายการแรกได้สถานะ "ไม่ใช่ข้อเท็จจริง": ที่ประชุมไม่ได้ระบุสกุลเงิน นั่นจึงเป็นสมมติฐานของเอเจนต์ รายการที่สองถูกพูดในที่ประชุมตรง ๆ จึงเป็น "ข้อเท็จจริง" ทั้งสองรายการรอให้คนยืนยัน และรายการ "ไม่ใช่ข้อเท็จจริง" กลายเป็นวาระของการประชุมครั้งถัดไป</b-why>
  <b-finding>
    <ex>บันทึกการประชุมกลายเป็นข้อกำหนดที่ทุกบรรทัดมีเครื่องหมายกำกับ</ex>
    <gen>คำพูดที่มีเวลากำกับทำให้การตรวจใช้เวลาไม่กี่วินาที และบรรทัดสมมติฐานแสดงว่าโมเดลเติมช่องว่างตรงไหน</gen>
    <do k="ควรทำ">ลองใช้ prompt นี้กับการประชุมหนึ่งครั้งของคุณ แล้วเทียบกับที่คุณจำได้</do>
  </b-finding>
</b-chapter>

<b-chapter id="levels" icon="layers" title="การแก้ใหญ่และการแก้เล็ก">
  <b-why align="left">เมื่อเอเจนต์หรือคนแก้ข้อกำหนด สิ่งสำคัญคือการแก้นั้นร้ายแรงแค่ไหน ความต่างง่าย ๆ คือ การแก้เล็กหาหลักฐานได้ ส่วนการแก้ใหญ่ไม่มีหลักฐาน การแก้เล็กไม่เปลี่ยนพฤติกรรมของระบบ: รายการทำงานเหมือนเดิม เปลี่ยนเพียงความมั่นใจหรือถ้อยคำ ตรวจเทียบกับแหล่งที่มาได้: หาคำพูดในการบันทึกการประชุม หรือดูในประวัติ Git ว่าความหมายไม่เปลี่ยน เอเจนต์จึงแก้เล็กเอง การแก้ใหญ่เปลี่ยนพฤติกรรมของระบบและไม่มีอะไรยืนยัน: แหล่งข้อมูลยังไม่มีการตัดสินใจแบบนั้น ไม่มีที่ให้ดึงหลักฐาน การแก้ใหญ่จึงเป็นเรื่องของคน: เอเจนต์เตรียมรายการ use case ที่ได้รับผลกระทบและร่าง แล้วเจ้าของข้อกำหนดตัดสินใจ หลังอนุมัติ ตัวการตัดสินใจ (ใคร เมื่อไร ทำไม) ถูกบันทึกใน Git และกลายเป็นแหล่งที่มาใหม่ หมายเลขเวอร์ชันในซอฟต์แวร์ทำงานแบบเดียวกัน: v1.0 → v1.1 หมายถึงการชี้แจงเล็กน้อย v1.0 → v2.0 หมายถึงการเปลี่ยนแปลงที่ต้องแจ้งให้ผู้คนรู้<b-proof href="https://semver.org/" quote="MAJOR version when you make incompatible API changes"/><b-proof href="https://semver.org/" quote="MINOR version when you add functionality in a backward compatible manner"/></b-why>
  <iso-art name="requirements-sources-facts-assumptions/versions"></iso-art>
  <b-why align="left">ด้านซ้ายของภาพคือเวอร์ชันต้นฉบับ v1.0 ตรงกลางคือการแก้เล็ก: เพิ่มบล็อกเล็ก ความหมายเดิม ตัวเลขที่สองเปลี่ยน (v1.1) ด้านขวาคือการแก้ใหญ่: เพิ่มบล็อกใหญ่ พฤติกรรมเปลี่ยน ตัวเลขแรกเปลี่ยน (v2.0) ใต้การแก้เล็กมีคำบรรยายว่า "พบหลักฐาน เอเจนต์ทำเอง" ใต้การแก้ใหญ่ว่า "ไม่มีหลักฐาน คนตัดสินใจ"</b-why>
  <b-rules sw="1.8">
    <rule icon="eye" t="ยืนยันข้อสันนิษฐานได้">สถานะกลายเป็น "ข้อเท็จจริง" ข้อความคงเดิม: การแก้เล็ก</rule>
    <rule icon="bug" t="ข้อสันนิษฐานถูกหักล้าง">ข้อความของรายการเปลี่ยน: การแก้ใหญ่</rule>
    <rule icon="ban" t="ข้อเท็จจริงเปลี่ยน">หากแหล่งที่มาเวอร์ชันใหม่เปลี่ยนพฤติกรรม การแก้นั้นเป็นการแก้ใหญ่: หลักฐานแสดงว่าแหล่งที่มาเปลี่ยนอะไร ส่วนจะต้องการเช่นนั้นหรือไม่เป็นเรื่องที่คนตัดสินใจ</rule>
    <rule icon="pause" t="ถ้อยคำ">การสะกดผิดหรือถ้อยคำที่ชัดขึ้นโดยความหมายเดิม ลงในประวัติการเปลี่ยนแปลง</rule>

<b-chapter id="cases" icon="git-branch" title="Use case">
  <b-why align="left">use case (ตามนิยาม คือคำอธิบายที่มีโครงสร้างของพฤติกรรมของระบบเมื่อตอบสนองต่อคำขอจากผู้กระทำภายนอก<b-proof href="https://en.wikipedia.org/wiki/Use_case" quote="structured description of a system’s behavior as it responds to requests from external actors"/>) คือหนึ่งสถานการณ์ของการใช้งานข้อกำหนด ข้อกำหนด “ชำระด้วยบัตร” มีสามสถานการณ์: ชำระปกติ ธนาคารปฏิเสธ และชำระซ้ำ เขียนออกมาเพราะการแก้หนึ่งครั้งมักแตะหนึ่งหรือสองสถานการณ์ และสถานการณ์เหล่านั้นคือสิ่งที่ต้องตรวจซ้ำ นี่คือจุดเชื่อมกับบทข้างบน: การแก้ใหญ่เปลี่ยนพฤติกรรม เอเจนต์จึงระบุ use case ที่ได้รับผลกระทบและเทสต์ของมัน การแก้เล็กไม่เปลี่ยนพฤติกรรม และเอเจนต์เพียงยืนยันว่า use case ยังเป็นเหมือนเดิม การแก้เล็กน้อยจึงไม่ต้องตรวจข้อกำหนดทั้งหมดซ้ำ</b-why>
  <iso-art name="requirements-sources-facts-assumptions/use-cases"></iso-art>
  <b-why align="left">ภาพแสดงเรื่องนี้ด้วยตัวอย่าง ด้านซ้ายคือข้อกำหนด “ชำระด้วยบัตร” ด้านขวาคือสาม use case: ชำระปกติ (ลูกค้าชำระทันที) ธนาคารปฏิเสธ (ข้อผิดพลาดและลองใหม่) และชำระซ้ำ (ป้องกันการตัดเงินซ้ำ) เครื่องหมายตกใจอยู่ที่ข้อที่สาม: สมมติว่าที่ประชุมตัดสินใจเปลี่ยนการป้องกันการตัดเงินซ้ำ นั่นเป็นการแก้ใหญ่ และแตะเฉพาะการชำระซ้ำ เอเจนต์ระบุ use case นั้นและเทสต์ของมัน ส่วนการชำระปกติและการที่ธนาคารปฏิเสธยังเหมือนเดิม</b-why>
  <b-pills>
    <pill>Case: เส้นทางปกติ</pill>
    <pill>Case: ข้อผิดพลาด</pill>
    <pill>Case: ซ้ำ</pill>
  </b-pills>
  <b-why align="left">ตัวอย่าง ที่ประชุมตัดสินใจว่าการชำระซ้ำภายในหนึ่งนาทีนับเป็นออเดอร์เดียวกัน นั่นเป็นการแก้ใหญ่ และแตะเฉพาะ use case "ซ้ำ" สำหรับข้อนี้ เอเจนต์ระบุเทสต์ที่ต้องปรับ เช่น “การชำระครั้งที่สองภายใน 30 วินาทีไม่ตัดเงินซ้ำ” use case "เส้นทางปกติ" และ "ข้อผิดพลาด" ยังเหมือนเดิม และเทสต์ของทั้งสองรันโดยไม่ต้องแก้ หากไม่มีรายการแบบนี้ use case ที่ได้รับผลกระทบจะถูกค้นพบโดยผู้ใช้</b-why>
  <b-finding>
    <ex>ข้อกำหนด “ชำระด้วยบัตร” แยกเป็นสามกรณี และการแก้เรื่องชำระซ้ำแตะเฉพาะกรณีที่สาม</ex>
    <gen>เมื่อแก้ใหญ่ เอเจนต์ระบุกรณีที่ได้รับผลกระทบ และเมื่อแก้เล็ก เอเจนต์ยืนยันว่ากรณีต่าง ๆ ไม่เปลี่ยน</gen>
    <do k="ควรทำ">หลังแก้ทุกครั้ง ให้ขอเอเจนต์ระบุกรณีที่ได้รับผลกระทบและเทสต์ของมัน</do>
  </b-finding>
</b-chapter>
