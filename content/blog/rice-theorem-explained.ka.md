რაისის თეორემის თანახმად, არც ერთ პროგრამას არ შეუძლია ნებისმიერი სხვა პროგრამის შესახებ ყოველთვის სწორად თქვას, როგორ იქცევა ის, მაგალითად, ჩამოჭრის თუ არა ფულს შეკვეთის გარეშე. ნებისმიერ პროგრამაში სხვა პროგრამის ჩადება შეიძლება და მაშინ პასუხი იმაზეა დამოკიდებული, დასრულდება თუ არა ჩადებული პროგრამა, რასაც არც ერთი პროგრამა ვერ გადაწყვეტს. ამიტომ პრაქტიკაში კითხვას ავიწროვებენ: ამოწმებენ კოდის ტექსტს, წესების პატარა მოდელს ან რთულ შემთხვევებს ადამიანს აბარებენ.

<b-chapter id="essence" icon="alert-circle" title="მთავარი: რას კრძალავს რაისის თეორემა">
  <b-why align="left">აკრძალვა ეხება ერთ შემმოწმებელს, რომელიც ყველა პროგრამისთვის ერთდროულად ვარგა: კონკრეტული ერთი პროგრამისთვის პასუხი ხშირად მოიძებნება. მკაცრი ფორმულირებით, თეორემა ამბობს, რომ არც ერთი პროგრამა ვერ შეამოწმებს ქცევის თვისებას, რომელიც ზოგ პროგრამას აქვს, ზოგს კი არა<b-proof href="https://en.wikipedia.org/wiki/Rice%27s_theorem" quote="Wikipedia: “Rice's theorem states that all non-trivial semantic properties of programs are undecidable.”"/>. ჰენრი გორდონ რაისმა ის 1951 წლის დისერტაციაში დაამტკიცა<b-proof href="https://en.wikipedia.org/wiki/Rice%27s_theorem" quote="Wikipedia: “The theorem is named after Henry Gordon Rice, who proved it in his doctoral dissertation of 1951 at Syracuse University.”"/>.</b-why>
  <b-why align="left">როგორ გავიგოთ ეს ყოფითი ენით. წარმოიდგინეთ შემმოწმებელი, რომელსაც ნებისმიერ პროგრამას აძლევენ და ეკითხებიან: „ჩამოჭრის თუ არა ოდესმე ფულს შეკვეთის გარეშე?“ შემმოწმებელი შეიძლება იყოს როგორც გინდათ ჭკვიანი, იმუშაოს რამდენსაც გინდათ და იცოდეს ყველა პროგრამირების ენა. თეორემა ამბობს, რომ მაინც იარსებებს პროგრამა, რომელზეც ის არასწორად უპასუხებს ან საერთოდ არ უპასუხებს. ეს თავად ამოცანის თვისებაა და შემმოწმებლის გაუმჯობესება მას ვერ მოხსნის, ისევე როგორც კონსტრუქციის გაუმჯობესება მუდმივ ძრავას ვერ შექმნის. ქვემოთ დიაგრამაზე შემმოწმებელი ლურჯი კუბია: ის პროგრამებს სათითაოდ უყურებს და თითოეულზე პასუხობს „იცავს“ ან „არღვევს“. მარჯვნივ ნარინჯისფერი პროგრამა სწორედ ამ შემოწმების წინააღმდეგაა აგებული, საკუთარი ტექსტიდან: მასზე პასუხი ან არასწორია, ან საერთოდ არ მოდის. სხვა შემოწმებას თავისი ასეთი პროგრამა ჰყავს.</b-why>
  <iso-art name="term:rice-theorem"></iso-art>
  <b-why align="left">წარმოიდგინეთ, მაღაზიაში ავტომატური შემოწმება დაამატეთ. ის კითხულობს გადახდის კოდის ყოველ ცვლილებას და პასუხობს: „ეს ცვლილება არასოდეს ჩამოჭრის ფულს შეკვეთის გარეშე“ ან „ჩამოჭრის“. იმისთვის, რომ ასეთ შემოწმებას ენდოთ, მას სამი რამ სჭირდება, რომლებიც ქვემოთ დიაგრამაზე დანომრილია.</b-why>

  1. **პასუხი ქცევაზე.** შემოწმებამ უნდა თქვას, რას გააკეთებს კოდი გაშვებისას: ჩამოჭრის თუ არა ფულს თუნდაც ერთ შესყიდვაზე იმ შესყიდვებიდან, რომლებიც მასში ოდესმე გაივლის. ეს შესყიდვები არასოდეს მთავრდება და ტესტებით ყველას ვერ გადაამოწმებთ.
  2. **ერთი შემოწმება ნებისმიერი ცვლილებისთვის.** წინასწარ ვერ შეავიწროებთ, როგორი კოდი მოვა: შემოწმება მუშაობს ნებისმიერ კოდზე, რომელსაც მიიღებს, იმაზეც კი, რომელიც მის მოსატყუებლადაა დაწერილი.
  3. **პასუხი ყოველ ცვლილებაზე.** მხოლოდ „ჩამოჭრის“ ან „არ ჩამოჭრის“, „არ ვიცი“-ს გარეშე: შემოწმებას merge-მდე მხოლოდ ცვლილების გატარება ან დაბლოკვა შეუძლია.

  <b-why align="left">ამ სამს გარდა, პასუხი სწორი უნდა იყოს: „არ ჩამოჭრის“ ნიშნავს „ნამდვილად არ ჩამოჭრის“. არსებობს შემოწმებები, რომლებიც ყოველთვის პასუხობენ, მაგრამ ხანდახან ცდებიან: ტესტები და ევრისტიკები. ისინი სასარგებლოა, მაგრამ სიტყვა-სიტყვით მათ ვერ ენდობით, და აქედან მხოლოდ სწორი შემოწმებები განიხილება.</b-why>

  <b-why align="left">რაისის თეორემა ამბობს: სწორი შემოწმება ამ სამივე თვისებით არ არსებობს; რომელიღაც ცვლილებაზე ის შეცდება ან ვერ უპასუხებს. დიაგრამაზე ეს ნარინჯისფერი ზოლია. თუ რომელიმე ერთ თვისებას მოხსნით, სწორი შემოწმება შესაძლებელი ხდება, ოღონდ დავიწროებული კითხვისთვის. რომელი მოვხსნათ, ეს პრაქტიკაში გაკეთებული არჩევანია: დიაგრამის ქვედა ნაწილში სამი ვარიანტია ნაჩვენები.</b-why>

    module payments {
      val ORDERS = Set(1, 2, 3)
      val CLIENTS = Set(1, 2)
      var orders: Set[int]     // created orders
      var paid: int -> int     // order → times charged
      var pending: int -> int  // customer → checked order (0 — none)
      action init = all {
        orders' = Set(), paid' = ORDERS.mapBy(o => 0), pending' = CLIENTS.mapBy(c => 0),
      }
      action createOrder(o: int): bool = all {
        not(orders.contains(o)),
        orders' = orders.union(Set(o)), paid' = paid, pending' = pending,
      }
      // step 1: the order exists and is unpaid
      action check(c: int, o: int): bool = all {
        pending.get(c) == 0, orders.contains(o), paid.get(o) == 0,
        pending' = pending.set(c, o), orders' = orders, paid' = paid,
      }
      // step 2: charge money
      action charge(c: int): bool = all {
        pending.get(c) != 0,
        paid' = paid.setBy(pending.get(c), n => n + 1),
        pending' = pending.set(c, 0), orders' = orders,
      }
      action step = {
        nondet o = ORDERS.oneOf()
        nondet c = CLIENTS.oneOf()
        any { createOrder(o), check(c, o), charge(c) }
      }
      val noPaymentWithoutOrder = ORDERS.forall(o => paid.get(o) > 0 implies orders.contains(o))
      val noDoubleCharge = ORDERS.forall(o => paid.get(o) <= 1)
    }

<b-chapter id="proof" icon="workflow" title="დამტკიცება ერთ მაგალითზე">
  <iso-art name="term:rice-proof"></iso-art>

  დამტკიცების იდეა რედუქციაა. თუ ერთი ამოცანის ამოხსნა შეიძლებოდეს, შეიძლებოდა სხვისიც, რომელიც უკვე ცნობილია, რომ არ იხსნება. მაშასადამე, პირველიც არ იხსნება. აქ პირველი ამოცანა ქცევის წესის შემოწმებაა, მეორე კი გაჩერების პრობლემა.

  აღნიშვნები: $P$ ნებისმიერი პროგრამაა, $w$ მონაცემებია, რომლებზეც ის ეშვება, $P(w)$ არის $P$-ს გაშვება $w$-ზე. გაჩერების პრობლემა ამოცანაა: ნებისმიერი $P$-სა და $w$-სთვის გაარკვიო, დასრულდება თუ არა ოდესმე $P(w)$.

  აიღეთ ნებისმიერი პროგრამა $P$ შემავალი მონაცემით $w$ და ააგეთ მისგან ახალი პროგრამა $Q$:

  $$Q(x) \;=\; \text{run } P(w)\text{; when it finishes, run } B(x)$$

  აქ $x$ მონაცემებია, რომლებზეც $Q$ ეშვება. ნაბიჯი $B(x)$ წესს არღვევს, უსასრულოდ მომუშავე პროგრამა კი არა. ამიტომ $Q$ დარღვევამდე მხოლოდ მაშინ მიდის, თუ $P(w)$ ოდესმე დასრულდება:

  $$Q \text{ breaks the rule} \iff P(w) \text{ halts}$$

  თუ წესის შემოწმება ყველა პროგრამისთვის არსებობდეს, $Q$-ზე ის იმასაც გვეტყოდა, ჩერდება თუ არა $P(w)$. მაგრამ ალან ტიურინგმა 1936 წლის ნაშრომში (გამოქვეყნდა 1937 წელს) დაამტკიცა, რომ ამ კითხვას არც ერთი პროგრამა ვერ პასუხობს, ეს გაჩერების პრობლემაა<b-proof href="https://en.wikipedia.org/wiki/Halting_problem" quote="Wikipedia: “Alan Turing proved in 1937 that the halting problem is undecidable.”"/>. მაშასადამე, წესის უნივერსალური შემოწმებაც არ არსებობს. წესი შეიძლება ნებისმიერი იყოს: „ფული შეკვეთის გარეშე“-ს ადგილას ქცევის ნებისმიერი თვისება ჯდება, რომელსაც განსხვავებული პასუხები აქვს.

  იგივე ნაბიჯები თანმიმდევრობით:

  1. აიღეთ ქცევის ნებისმიერი წესი, რომელსაც ზოგი პროგრამა არღვევს, ზოგი კი არა. მაშასადამე, რომელიღაც პროგრამა მას არღვევს. იმ პროგრამის ნაწილი, რომელიც წესს არღვევს, არის ნაბიჯი $B$.
  2. აიღეთ ნებისმიერი პროგრამა $P$ და მისი შემავალი მონაცემები $w$, რომლებისთვისაც კითხვა ისაა, ჩერდება თუ არა $P(w)$.
  3. შეადგინეთ $Q$: ჯერ $P(w)$, შემდეგ $B$. შეერთება მარტივი მექანიკური პროცედურაა, რომლის დაწერაც ერთ წუთში შეიძლება.
  4. $Q$ გადაეცით წარმოსახვით უნივერსალურ შემოწმებას. მისი პასუხი „არღვევს“ ნიშნავს „$P(w)$ გაჩერდა“, ხოლო „არ არღვევს“ ნიშნავს „არ გაჩერდა“.
  5. ეს გაჩერების პრობლემის ამოხსნაა, რომელიც არ არსებობს. მაშასადამე, უნივერსალური შემოწმებაც არ არსებობს.

  სიზუსტისთვის ერთი დათქმა. აგება გულისხმობს, რომ პროგრამა, რომელიც უსასრულოდ მუშაობს და არაფერს აკეთებს, წესს არ არღვევს. თუ რომელიმე წესისთვის ასე არ არის, აიღეთ საპირისპირო წესი: მისი შემოწმება უფრო მარტივი არ არის და მსჯელობა სიტყვასიტყვით მეორდება.

  <b-why align="left">**რამდენად მკაცრია ეს.** ორივე ნახევარი დამტკიცებულია: რაისის თეორემა და CAP-ის დამტკიცება გამოქვეყნებულია. გამოსავლების დამთხვევა ავტორის დაკვირვებაა; ორივე შემთხვევისთვის ერთი თეორემა არ არსებობს. თავად ბრიუერმა მოგვიანებით გააფრთხილა, რომ ფორმულა „სამიდან ორი“ (იდეა, რომ სამი თვისებიდან მხოლოდ ორი შეიძლება გქონდეთ) ზედმეტად ამარტივებს<b-proof href="https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/" quote="Eric Brewer: “The «2 of 3» formulation was always misleading”"/>: სინამდვილეში ეს სკალაა და არჩევანი მხოლოდ დაყოფის დროს ჩნდება. შემოწმებებშიც ასეა: მნიშვნელოვანია, რამდენად ხშირად ამბობს შემოწმება „არ ვიცი“ ან ცდება.</b-why>
  <b-finding>
    <ex>ავტომატური შემოწმება გაჭედილი ტესტის გაშვებას ელოდება. უფრო დიდხანს ლოდინი სერვერის მიერ კავშირის ლოდინს ჰგავს; ტაიმაუტზე მოჭრა და „გავიდა“-ს თქმა კი სერვერს, რომელიც მოძველებული ასლიდან პასუხობს.</ex>
    <gen>ლოდინი და გამოცნობა ორივე აკრძალვის საერთო გამოსავალია. დროის წინასწარ შეზღუდვა პროგრამების შემოწმებაში განშტოებას აქრობს, ქსელში კი მხოლოდ „სამუდამოდ დაელოდე“-ს „ვიცი, რომ კავშირი გაწყვეტილია“-დ აქცევს.</gen>
    <do>ყოველ ავტომატურ შემოწმებას მიეცით დროის ლიმიტი და წინასწარ გადაწყვიტეთ, რას ნიშნავს მისი გადაჭარბება: „არ ვიცი“ ადამიანისთვის გადაცემით, თუ „დარღვეულია“.</do>
