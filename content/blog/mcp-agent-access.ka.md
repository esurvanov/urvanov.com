MCP აგენტს აკავშირებს სამუშაო სისტემებთან, ამიტომ ის ფაქტებს კითხულობს წყაროდან და არა გადმოცემული ვერსიიდან. ეს მარტივი და სწრაფია: საკმარისია გაიგოთ, რა პრობლემას წყვეტს, და დაყენება თავად აგენტს მიანდოთ. ქვემოთ: იდეა, დაკავშირება, რას იძლევა და რა უფლებები უნდა მიენიჭოს. QA-ს მაგალითი MCP-ით განხილულია სტატიაში [QA აგენტით MCP-ის საშუალებით](/blog/bug-report-to-reproduction-agent/#mcp).

<b-why align="left">MCP ერთი საერთო შტეფსელია, USB-ის მსგავსი. აგენტს Jira-სთან ან GitLab-თან რომ დააკავშირებთ, მონაცემებს იქიდან თავად აიღებს. <a href="https://modelcontextprotocol.io/docs/getting-started/intro" target="_blank" rel="noopener">დეტალურად</a></b-why>
<b-why align="left">სურათზე ნაჩვენებია მონაცემთა ორი გზა. პირველზე ადამიანი ამოცანას აგენტს თავისი სიტყვებით უყვება და დეტალები გზაში იკარგება. მეორეზე აგენტი სისტემას MCP-ით თავად კითხულობს და ხედავს ყველაფერს, რასაც ადამიანი ხედავს. MCP (Model Context Protocol) ღია სტანდარტია, რომელიც AI აპლიკაციებს გარე სისტემებთან აკავშირებს<b-proof href="https://modelcontextprotocol.io/docs/getting-started/intro" quote="MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems."/>. აგენტს აქვს MCP კლიენტი, სისტემას — MCP სერვერი, ხოლო სერვერი აგენტს ეუბნება, რომელი მონაცემები და მოქმედებებია ხელმისაწვდომი.</b-why>

<b-why align="left">აგენტის კონტექსტი ის ყველაფერია, რასაც ის ერთდროულად ხედავს (საუბარი აგენტთან, პროექტის ფაილები). სხვა კონტექსტები ყველაფერი დანარჩენია (GitLab, Jira, შეხვედრების ჩანაწერები, ცოდნის ბაზა). მათ შორის ხიდი MCP-ია: აგენტს აქვს MCP კლიენტი, სისტემას — MCP სერვერი.</b-why>

<b-why align="left">სურათის მარცხენა მხარეს აგენტის კონტექსტია: საუბარი მასთან და პროექტის ფაილები, რომლებსაც ერთდროულად ხედავს. მარჯვნივ სხვა სისტემებია: GitLab, Jira, tldv შეხვედრების ჩანაწერებით, Confluence ცოდნის ბაზით. სანამ MCP არ არის დაკავშირებული, აგენტი მათ ვერ ხედავს. მათ შორის ხიდი ორი ნაწილისგან შედგება: MCP კლიენტი აგენტის მხარეს და MCP სერვერი სისტემის მხარეს.</b-why>
