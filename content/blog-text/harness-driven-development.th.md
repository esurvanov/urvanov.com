**สรุป:**

**ในตัวอย่างนี้:** พรอมต์แก้คำตอบเดียว บริบทแก้สิ่งที่โมเดลรู้ และ harness แก้ทุกการรันของเอเจนต์ในอนาคต

**โดยทั่วไป:** Harness-Driven Development คือการทำงานในขั้นที่สาม: นักพัฒนาเขียนโค้ดน้อยลงและใช้เวลามากขึ้นกับการตั้งสภาพแวดล้อมที่เอเจนต์เขียน ตรวจ และแก้ไขเอง

**ก้าวต่อไป:** จดความผิดพลาดสามครั้งล่าสุดของเอเจนต์ และทำเครื่องหมายว่าแต่ละอย่างควรแก้ให้จบถาวรได้ในขั้นไหน

## วงจร HDD

หลักการของ Mitchell Hashimoto: เมื่อเอเจนต์ทำพลาด ให้เปลี่ยน harness เพื่อไม่ให้ความผิดพลาดนั้นเกิดซ้ำได้ Faros

**สรุป:**

**ในตัวอย่างนี้:** ความผิดพลาดที่ sensor จับได้ถูกใส่เข้า harness เป็นกฎใหม่ และเอเจนต์ได้กฎนั้นในทุกการรันถัดไป

**โดยทั่วไป:** ผลลัพธ์ที่แก้ด้วยมือช่วยได้ครั้งเดียว กฎใน harness (คำสั่ง เทสต์ หรือ hook) ใช้กับงานในอนาคตทั้งหมด harness จึงแม่นยำขึ้นเรื่อย ๆ โดยไม่ต้องเปลี่ยนโมเดล

**ก้าวต่อไป:** ตั้งกฎข้อหนึ่ง: ความผิดพลาดของเอเจนต์ทุกอย่างที่ต้องแก้ด้วยมือ ต้องกลายเป็นหนึ่งบรรทัดในคำสั่งหรือหนึ่งเทสต์ภายในวันเดียวกัน

**ก้าวต่อไป:** จัดไฟล์ใน harness ของคุณลงเก้าช่อง และตรวจว่าไม่มีไฟล์ของ Expectation หรือ Observation ที่อ้างถึง Loop

## วงจรสองชั้น

**วงจรชั้นเดียว:** แก้การกระทำภายใต้กฎเดิม

**วงจรสองชั้น:** เปลี่ยนตัวกฎเอง

**Patch ที่ไม่มีการทำนายใหม่:** แก้ด้วยกฎ

**คำบ่นหลายเรื่อง:** ทดสอบก่อนว่ามีสาเหตุร่วมหรือไม่

**กฎใหม่:** ยอมรับเมื่อกรณีเก่าอธิบายตามได้

**ไม่มีการตรวจจากภายนอก:** ทิ้งไป พร้อมบันทึกไว้

วงจรใช้กับตัวเองด้วย: ทุกการรันจบด้วยความเสี่ยงที่เหลือ ไม่เคยจบด้วยสถานะ “เสร็จแล้ว”

**สรุป:**

**ในตัวอย่างนี้:** ชุดของ patch คำบ่น กฎใหม่ และการตรวจจากภายนอก เป็นสี่หลักการที่ตรวจได้ ซึ่ง Loop ใช้ตัดสินว่าจะแก้การกระทำหรือเปลี่ยนกฎ

**โดยทั่วไป:** วงจรชั้นเดียวแก้ผลลัพธ์ภายใต้กฎเดิม วงจรสองชั้นเปลี่ยนตัวกฎ และทำตามหลักการที่ตรวจได้ harness จึงเรียนรู้โดยไม่ลอยไปตามการแก้แบบสุ่ม

**ก้าวต่อไป:** เมื่อการแก้แบบเดิมโผล่มาเป็นครั้งที่สาม ให้หยุดแล้วถามว่ากฎข้อไหนเป็นต้นเหตุ เปลี่ยนกฎก็ต่อเมื่อกฎใหม่อธิบายกรณีเก่าได้ด้วย

**ก้าวต่อไป:** สำหรับกฎแต่ละข้อในคำสั่งของเอเจนต์ ให้ถามว่าเทสต์หรือ linter ตรวจได้ไหม ถ้าได้ ย้ายไปไว้ที่นั่น

**ก้าวต่อไป:** เริ่มจากชั้นแรก: รัน linter และตัวจัดรูปแบบทุกครั้งที่เอเจนต์รัน แล้วเพิ่มกฎเรื่องขอบเขตโมดูลหนึ่งข้อ

**ก้าวต่อไป:** ต่อเทสต์และ linter เข้ากับ hook ที่เอเจนต์รันหลังการแก้ทุกครั้ง เพิ่มจาก CI

## คนสำคัญตรงไหน

Harness

สไตล์ · ชนิดข้อมูล · เทสต์ · ขอบเขต

คน

สถาปัตยกรรม · ผลิตภัณฑ์ · กฎใหม่

"harness ที่ดีเก็บคนไว้ในวงจรและชี้ความสนใจของคนไปยังจุดที่สำคัญที่สุด" — ถอดความจาก Martin Fowler

**สรุป:**

**ในตัวอย่างนี้:** harness รับการตรวจส่วนใหญ่ไป คนเก็บการตัดสินใจและงานปรับปรุง harness ไว้

**โดยทั่วไป:** นักพัฒนาที่มีประสบการณ์พก harness โดยนัยไว้ในหัว คือความรู้เรื่องสถาปัตยกรรม นิสัยของทีม และความรู้สึกต่อความเสี่ยง HDD ย้ายความรู้นั้นมาเป็นกฎที่ชัดเจน เอเจนต์ทุกการรันจึงได้รับความรู้นั้น

**ก้าวต่อไป:** หลังรีวิวโค้ดของเอเจนต์ทุกครั้ง ให้จดความเห็นหนึ่งข้อที่เจอซ้ำ ๆ แล้วเปลี่ยนเป็นกฎ

## HDD กับ spec

**Spec:** ผลลัพธ์ที่ต้องการ

**Harness:** ตรวจอย่างไรว่าได้แล้ว

**โค้ดที่ยอมรับ:** ไม่ต้องรีวิวด้วยมือทีละบรรทัด

"Specs define the target state, the harness is the control system" — Loiane Groner อ่านเรื่อง spec เพิ่มเติมในการบรรยาย Spec-Driven Development in practice

**สรุป:**

**ในตัวอย่างนี้:** spec ตอบว่า "เรากำลังสร้างอะไร" harness ตอบว่า "เรารู้ได้อย่างไรว่าสร้างเสร็จ"

**โดยทั่วไป:** ถ้าไม่มี spec harness ก็ไม่มีอะไรให้ตรวจ และถ้าไม่มี harness spec ก็เป็นแค่เอกสาร สองอย่างรวมกันทำให้ยอมรับโค้ดของเอเจนต์จากผลการตรวจ แทนการอ่านทุกบรรทัด

**ก้าวต่อไป:** สำหรับข้อกำหนดแต่ละข้อใน spec ให้จดว่าเทสต์หรือการตรวจแบบไหนจะยืนยันว่าเป็นไปตามข้อกำหนด
