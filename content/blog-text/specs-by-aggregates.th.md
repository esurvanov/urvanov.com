ตัวเลขเป็นตัวอย่างประกอบ วิธีที่ OpenSpec จัดวาง spec และการเปลี่ยนแปลง: โฟลเดอร์ specs/ และ changes/ ส่วนการเปลี่ยนแปลงที่เสร็จแล้วจะย้ายไปคลังเก็บถาวร

**สรุป:**

**ในตัวอย่างนี้:** สิบสองฟีเจอร์ให้ spec สิบสองฉบับ และการจองถูกอธิบายอยู่ในเจ็ดฉบับ ซึ่งแต่ละฉบับต่างกันเล็กน้อย ในพจนานุกรม ฟีเจอร์ชุดเดียวกันเพียงเพิ่มบรรทัดลงในสี่รายการของ aggregate

**โดยทั่วไป:** เมื่อ spec ผูกกับการเปลี่ยนแปลงหรือฟีเจอร์ ทุกงานจะเพิ่มไฟล์ และแนวคิดเดียวกระจัดกระจายไปหลายที่ เมื่อหน่วยคือ aggregate จำนวนรายการถูกจำกัดโดยโดเมนเอง และฟีเจอร์เพียงเพิ่มข้อกำหนดลงในรายการ

**ขั้นต่อไป:** ไล่หาแนวคิดที่ปรากฏใน spec สามฉบับขึ้นไป แล้วให้แต่ละแนวคิดมีรายการเดียวในพจนานุกรม ให้ spec ของฟีเจอร์ลิงก์ไปที่รายการนั้น แทนการเล่าซ้ำ

## ระดับข้อกำหนดตาม RFC 2119

คำ ความหมาย ความเข้ม การตรวจ

MUSTจำเป็นต้องมี เทสต์อัตโนมัติบล็อก

MUST NOTห้าม เทสต์อัตโนมัติบล็อก

SHOULDค่าเริ่มต้น เบี่ยงได้เมื่อมีเหตุผล รีวิวเตือน

MAYอนุญาต ไม่มีไม่ตรวจ

MUST = SHALL

คำและความหมายอ้างอิง RFC 2119 แต่ละคำสอดคล้องกับการตรวจแบบของตัวเอง

**สรุป:**

**ในตัวอย่างนี้:** ในรายการการจอง "ช่วงเวลาต้องไม่ทับกัน" เป็น MUST ที่ตรวจด้วยเทสต์ ส่วน "การยืนยันส่งไปช่องทางเดียวกัน" เป็น SHOULD ที่ดูตอนรีวิว

**โดยทั่วไป:** คำที่ใช้กำกับข้อกำหนดบอกทันทีว่าจะตรวจอย่างไรและต้องทำอะไรเมื่อฝ่าฝืน เอเจนต์อ่าน MUST เป็นขอบเขต และ SHOULD เป็นค่าเริ่มต้น และไม่สับสนสองอย่างนี้

**ขั้นต่อไป:** เขียนข้อกำหนดใน spec ใหม่ด้วยสี่คำนี้ และวางเทสต์ที่ตรวจไว้ข้างทุก MUST

Description: A meeting room booked for an interval.

```
Invariants:

  - MUST: active bookings of a room never overlap

  - MUST: held → confirmed → closed, forward only

  - MUST: held unconfirmed for 15 min → closed

  - SHOULD: confirm in the channel it was made in

```

```

```

```

```
6 มาจากฟีเจอร์ไหน

ตัวอย่างนี้สมมติขึ้น ศัพท์อ้างอิง Martin Fowler: DDD Aggregate

**สรุป:**

**ในตัวอย่างนี้:** การจองทั้งหมดอยู่ในการ์ดใบเดียว: ที่อยู่ ข้อกำหนดสี่ข้อ คำสั่งสามคำสั่ง สิทธิ์ ลิงก์ และฟีเจอร์ต้นทาง

**โดยทั่วไป:** aggregate คือขอบเขตที่ข้อกำหนดเป็นจริงเสมอภายใน และเปลี่ยนได้ผ่านคำสั่งของตัวเองเท่านั้น การ์ดจึงวางกฎไว้ข้างทางเดียวที่จะทำให้กฎเสียหายได้

**ขั้นต่อไป:** ทำการ์ดหกช่องให้ทุก aggregate หากข้อกำหนดข้อใดไม่เข้ากับ aggregate ใดเลย มักแปลว่ายังไม่ได้ตั้งชื่อ aggregate นั้น

## Bounded context

booking

Reservation Room TimeSlot

billing

Invoice Tariff

access

Pass Level

ลิงก์ระหว่าง context ใช้ id เท่านั้น billing::Invoice→ id → booking::Reservation access::Pass→ id → booking::Reservation

“Level”

booking::Room.floorชั้น

access::Levelระดับสิทธิ์

คำเดียว สองศัพท์ ป้ายต่างกัน

หนึ่งศัพท์ = หนึ่งรายการ ลิงก์ในรูป [[ctx::Name]] คำเดียวกัน → แยกรายการ พจนานุกรมเปลี่ยนไปพร้อมกับ spec

แนวทางนี้คือ Bounded Context และ Ubiquitous Language

**สรุป:**

**ในตัวอย่างนี้:** ใบแจ้งหนี้และบัตรผ่านอ้างถึงการจองด้วย id และไม่รู้อะไรเกี่ยวกับภายในของมัน "Level" หมายถึงชั้นใน booking และระดับสิทธิ์ใน access ซึ่งเป็นสองรายการแยกกัน

**โดยทั่วไป:** context คือพื้นที่ที่ทุกคำมีความหมายเดียว เมื่อคำหนึ่งปรากฏในสอง context ให้สร้างสองศัพท์ที่มีป้ายต่างกัน มิฉะนั้นเอเจนต์จะเอากฎจากที่หนึ่งไปใช้กับอีกที่หนึ่ง

**ขั้นต่อไป:** จัด aggregate ของคุณเข้า context แล้วหาคำที่ปรากฏในสอง context ให้แต่ละคำมีรายการแยกกันและป้ายต่างกันในหน้าจอ
